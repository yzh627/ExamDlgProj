为什么让 AI 下载会更顺？
浏览器下载文件时，Windows 会给它打一个「来自互联网」的标记，随后弹蓝窗提醒。 而命令行工具下载的文件不会带这个标记，弹窗这一步往往就省掉了。

不过要说明两点：

  • 如果是 Smart App Control（Win11 22H2 起的功能）拦的，命令行下载也躲不过——它看的是"有没有数字签名"，跟下载方式无关。而且它没有「仍要运行」按钮。
  • AI 会帮你核对哈希，这一步它不会省。

三、那个蓝色警告到底是什么

如果你双击时看到：

「Windows 已保护你的电脑」
Microsoft Defender SmartScreen 阻止了无法识别的应用启动

先别慌，这不是病毒，也不是程序有问题。

原因很简单：这个软件目前没有购买商业数字签名证书。Windows 对没签名的程序会弹蓝窗提醒，这是它的常规保护机制。

签名是什么，为什么重要

打个比方。软件签名就像画家在画作右下角签名。

一张没签名的画，你只能相信递给你的人说"这是我画的"。一张签了名的画，你可以拿这个签名去问"这个人是不是真的画过这幅画"——因为签名用的是只有作者本人才有的私钥，别人伪造不了。

三件需要说清的事

1. 弹窗 ≠ 有病毒。它说的是"我不认识这个人"，不是"这个人是坏人"。反过来讲，如果有人做了个仿冒的 Chrome，没有签名反而是好事，系统会拦一下。

2. 只影响你自己下载的程序。你从官网下 Chrome 从来不会看到蓝窗，因为它有签名。

3. 签名不能解决什么。这点最容易被误解——

签名 ≠ 一定不弹蓝窗

很多人以为买了最贵的证书（几千元那种）就能直接跳过警告。这个说法从 2024 年 8 月起就不成立了——微软取消了「增强验证证书（EV）立即豁免」的政策，现在普通证书和增强证书在这一点上完全一样。

新发布的软件不管用什么证书签名，初期都可能被弹窗。决定因素是下载量积累出来的信誉，不是证书贵不贵。

所以网上那些"买 EV 证书就是为了不弹窗"的建议，2026 年已经不值得花那个钱了。

四、怎么确认文件没被人动过

因为没有签名，你可以自己核对。SHA256 相当于文件的"指纹"，改动一个字节就会完全不同。

对口升学练习系统_安装程序.exe
7269185e25692ed94456d5ebdb4ccdf75d5dea3cef7dd099219a84884796eeb5

怎么算（Windows 自带，不用装任何软件）

  1. 解压 zip
  2. 在解压出来的文件夹里，按住 Shift 点右键 → 选「在此处打开 PowerShell 窗口」
  3. 粘贴这一行，回车
    certutil -hashfile ".\对口升学练习系统_安装程序.exe" SHA256
  4. 逐字符比对。完全一致 → 官方原版，未被篡改。
    不一致 → 别运行，来问我。
SHA256 有个特点：哪怕文件只改了 1 个字节，算出来的值会变得完全无关。所以它能有效证明"文件没被改过"。

脚本会：

  1. 自己找安装程序——会在 U 盘、桌面、下载、各个盘根目录里搜
  2. 先验明正身——确认这确实是本产品的安装程序才动手
  3. 自动装好、自动建桌面和开始菜单快捷方式

进阶用法

想先预演一遍看会装到哪（不实际安装）：

.\静默安装.bat /DRYRUN

想装到别的位置：

.\静默安装.bat /D=D:\练习系统

批量装机前，提前把警告一次性解决掉：

在装机的电脑上，选中解压出来的所有文件 → 右键 → 属性 → 勾选「解除锁定」→「应用」。之后整批装机都不会再弹蓝窗。

顺便一提：用 7-Zip 解压出来的文件不会继承这个标记，所以「先解锁再分发」这个做法对压缩包分发特别有效。

技术说明

这部分可以跳过，不影响使用。

为什么自己写安装器，没用 NSIS

用过几个现成方案，装出来的东西都有不满意的地方：体积涨得厉害、卸载容易留残留、没法定制"装到非空目录时先问一句"这种交互。

而且有个硬约束：学生的电脑环境不能假设。机房机器经常缺组件、系统版本混杂、权限策略各异。所以干脆自己写。

整个安装包只有一个 exe，5.8 MB，里面装了什么

所有东西都塞在 PE 文件的资源段（.rsrc）里：

对口升学练习系统_安装程序.exe  (5.8 MB)
└── .rsrc 资源段
    ├── x64 主程序        2.8 MB
    ├── x86 主程序        2.2 MB
    ├── 加密题库          288 KB
    ├── 卸载程序          222 KB
    ├── 程序清单
    └── 界面图片

安装时用 Windows API 逐个挖出来释放到磁盘。双击即用，不需要解压中间层。

同时提供 x64 和 x86 两个版本，是因为老机房还有 32 位系统在跑——不用问学生"你系统是几位的"。

题库是加密内嵌的

题库不是明文打包，而是加密成 questions.dat 再塞进安装程序。理由很单纯：题库是这套工具的核心内容，明文躺在安装包里容易被单独抽出来传。

静默安装脚本的"验明正身"

批量装机时会遇到：老师的 U 盘里可能有各种奇奇怪怪的可执行文件，脚本不该随便挑一个就装。所以做了三重校验，宁缺毋滥：

第一层  粗筛（只说明"可能是"，不作数）
  · 文件名含「对口」「升学」「练习」「河北」等字样
  · 体积在 1 MB ~ 40 MB 之间
  · 名字带「卸载」的直接排除

第二层  细验（过其一才算数）
  A) 算 SHA256 与内嵌校验值比对  → 同版本必然命中
  B) 读文件版本信息：
     ProductName 含「对口升学」
     且 CompanyName 含「一个中职生」
     且 FileDescription 含「安装程序」

第三层  都不过
  · 双击模式：要求人工按 Y 确认
  · 自动化模式：直接拒绝，绝不勉强

有意思的是 B 这条。SHA256 会随版本变，但版本信息里的产品名是稳定的——升级版本后即使哈希对不上，只要还是本产品，依然能认出来。

安全加固补了四轮

发布前把二进制的安全标志全读了一遍，结果发现自己项目"该开的一个没开"。

项目之前现在
ASLR已开显式写死
DEP/NX已开显式写死
CFG 控制流保护4 个 exe 全缺已开启
CET 影子栈（x64）缺已开启
代码签名无待申请

CFG 那个尤其典型。grep 了一遍工程文件：

$ grep -c ControlFlowGuard ExamDlgProj.vcxproj
0

整个项目在编译层面就没开过控制流保护，SDLCheck、BufferSecurityCheck 这些关键词出现次数也全是 0——不是关了，是从来没打开过。

构建搬到 CI 后，炸出了四个雷

把整个构建搬到 GitHub Actions，结果在干净环境里连续炸了四次。每一个都是本机侥幸没暴露的问题：

① 版本探测被功能目录骗了

# 原来的写法：挑"最新"的 SDK
Get-ChildItem $inc -Directory |
  Sort-Object Name -Descending | Select -First 1

SDK 的 Include 目录下不只有版本目录，还有 wdf（驱动开发包）这种功能目录。字符串倒序时 'w' 的编码值比数字大，所以 wdf 会被选中，拼出 bin\wdf\x64\mt.exe 这种不存在的路径。

报错说"找不到 mt.exe"，让我以为是 SDK 没装对——真因却是版本探测写错了。

② 临时目录指向不存在的路径

脚本里写了 $env:TMP = "x64\Debug"，而那个目录只在我本机存在（因为以前编过 Debug 版）。干净机器上链接直接报 LNK1104。

③ 工具链没装

microsoft/setup-msbuild 只装 MSBuild 本体，不含 C++ 编译器。而且只装 SDK 的话，mt.exe（清单工具）可能落在 WDF 目录里，而它是链接内嵌清单时必须调用的。

④ 辅助步骤掩盖了真错误

上传构建产物的步骤配了 if: always()（本意是"无论成败都上传"）。构建失败时目录是空的，它照样跑，然后报「未发现文件」，把真正的 SDK 错误盖住了。诊断时要多绕一圈才知道该看哪。

这四个雷的共同点：本机环境恰好提供了某些东西，脚本没去检查。CI 是个干净环境，专门用来炸出这类问题。
