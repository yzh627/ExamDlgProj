# 代码签名与发布

本文说明本项目如何获得代码签名，以及发布前需要检查什么。

## 现状与目标

Windows 11 22631 起 Smart App Control（SAC）默认开启，它会检查**执行链上的每一个
二进制**（主程序、安装器、卸载器、释放出来的临时文件）。任一项未签名或信誉不足，
整个安装过程都可能被拦。

本项目不使用付费证书，采用 **SignPath Foundation** 免费方案：
OV 级代码签名，私钥存放在 SignPath 的 HSM 中，**不落在本机、不进仓库**。

代价是必须满足 SignPath 的开源条件，其中最关键的一条：
**构建过程必须完全自动化**。SignPath 要向用户证明"这个 exe 确实由你仓库里的源码构建而来"，
本地手工编译再上传是不被接受的。

## SignPath 的资格条件

| 条件 | 本项目现状 |
|---|---|
| OSI 认可的开源许可证 | ✅ 已补 `LICENSE`（MIT） |
| 公开仓库 | ⬜ 待创建 GitHub 仓库并推送 |
| 构建完全自动化 | ✅ 已补 `.github\workflows\build-and-sign.yml` |
| 账号启用 MFA | ⬜ GitHub 与 SignPath 双方都要开 |
| 项目有实际发布版本 | ⬜ 需先有一个 Release |
| 下载页有功能说明 | ✅ 已补 `README.md` |
| 无恶意代码、无专有组件 | ✅ 仅链接 MFC 与 VC 运行库（系统库，可接受） |
| 团队分工（作者/评审/批准） | ✅ 单一维护者天然满足 |

## 申请步骤

1. 在 GitHub 创建**公开**仓库，把本项目推送上去。
2. 在 GitHub 与 SignPath 账号上**都启用 MFA**（硬性要求）。
3. 先打一个 `v1.0.0` 标签让 CI 跑出**未签名**的 Release —— SignPath 要求"已有可签名的发布版本"。
4. 到 <https://signpath.org/apply> 提交申请，提供：
   - 仓库 URL
   - 许可证（MIT）
   - 下载页 URL（Release 页）
   - 项目简介
   - 维护者身份
5. 等待人工审核（通常 1–3 个工作日）。
6. 通过后会得到一个 SignPath Organization。在后台配置：
   - **Trusted Build System** → 添加 GitHub，授权你的仓库
   - **Artifact Configuration** → 指定要签名的 PE 文件
   - **Signing Policy** → 通常命名为 `release-signing`

## 在 GitHub 仓库配置 Secrets

Settings → Secrets and variables → Actions：

| 名称 | 类型 | 来源 |
|---|---|---|
| `SIGNPATH_API_TOKEN` | Secret | SignPath 后台 My Profile → API Tokens，权限选 **Submitter** |
| `SIGNPATH_ORGANIZATION_ID` | Variable | SignPath 后台 URL 里的 GUID |
| `SIGNPATH_PROJECT_SLUG` | Variable | 项目设置页 |
| `SIGNPATH_SIGNING_POLICY_SLUG` | Variable | 通常是 `release-signing` |

**一个都不配也能跑通** —— 工作流会跳过签名，产出未签名版本。
但要注意：**此时签名者不是"一个中职生"，而是 SignPath Foundation**。
这是 SignPath 的机制：他们用自己的证书为项目背书，身份归他们。
好处是证书有真实公信力，代价是签名者显示为 SignPath Foundation。

## 为什么必须签 4 个文件

SAC 检查的是执行链，不只是主程序。本项目的安装器会把主程序和卸载器
从资源段释放到磁盘再执行，所以这些文件都会独立出现在执行链上：

1. `对口升学练习系统_安装程序.exe` — 学生双击的那个
2. `ExamDlgProj.exe` — x64 主程序
3. `ExamDlgProj_32位.exe` — x86 主程序
4. `Uninst.exe` — 卸载程序

漏签任何一个，SAC 都可能整体拦截。这也是 `tools\rebuild.ps1` 把 4 个文件
写进签名清单的原因。

## 私钥红线

- 私钥在 SignPath 的 HSM 里，**永不导出、永不落地**。
- 本仓库不存放任何 `.pfx` / `.p12` / `.pem` / `.key` / `.p8`，
  `.gitignore` 已强制拦截，并有自检脚本复查。
- `SIGNPATH_API_TOKEN` 只存在于 GitHub Secrets，不进代码、不进日志、不进聊天记录。
- 若将来改用付费证书（云 HSM），同样遵守：只传保管库引用名，不传密钥文件。

## 签名也未必一次通过

签名有效 ≠ 一定不拦。SAC 还看云端信誉，新发布、下载量小的程序仍可能被拦。
若被拦，**不要关闭系统防护**，按顺序排查：

1. 看 SAC 的判定日志（这是最直接的证据）：

   ```
   事件查看器 → 应用程序和服务日志 → Microsoft → Windows → CodeIntegrity → Operational
   ```

   - 事件 ID **3076** = 评估模式（本来会拦）
   - 事件 ID **3077** = 强制模式（实际被拦了）

2. 确认 4 个文件都已签名且带时间戳：

   ```powershell
   powershell -NoProfile -ExecutionPolicy Bypass -File tools\check_release_signing.ps1
   ```

3. 确认学生是从 **GitHub Release 官方页**下载，而不是聊天软件转发的压缩包。

不建议的做法：关闭 SmartScreen / Defender / SAC、加壳、使用"免杀"工具、
购买来路不明的共享证书。这些既解决不了根因，也会损害你自己电脑的安全。

## 证书有效期提醒

代码签名证书有效期已缩短到 460 天（CA/B Forum 提案 CSC-31，2026-03-01 生效）。
SignPath 会在到期前处理续签，但仍建议在 Release 时留意有效期字段。
带 RFC 3161 时间戳的签名在证书到期后依然有效。

## 复测清单

| # | 检查 | 判据 |
|---|---|---|
| 1 | 仓库无密钥材料 | `.gitignore` 生效，`check_release_signing.ps1` 第 1 项通过 |
| 2 | 构建可全自动复现 | GitHub Actions 跑通，无需本地干预 |
| 3 | 4 个文件全部签名 | 自检脚本第 2 项 4 行全为 `Valid` |
| 4 | 均带时间戳 | 自检脚本第 2 项无"缺时间戳" |
| 5 | 加固标志到位 | 自检脚本第 3 项 CFG 通过（需重新编译才生效） |
| 6 | 产物一致 | 自检脚本第 4 项：bat 哈希 / zip 成员 / 两份安装程序一致 |
| 7 | 干净机实测 | Defender 实时防护开启的机器上，保留 MOTW 直接运行 |
| 8 | 拦截可归因 | 若被拦，CodeIntegrity 日志能说明具体原因 |
