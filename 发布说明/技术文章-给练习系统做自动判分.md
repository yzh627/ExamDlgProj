# 我给河北对口升学计算机技能测试做了一个练习系统，它能自动判分

> 这是我做的一个小工具，开源了，也想说说它背后几个有意思的技术点。

## 为什么做这个

对口升学计算机类考试有笔试和机考，机考占了相当大的比重。
学生练习时最大的痛点是：**在家写的代码，自己看不出对错**。

于是我做了这个练习系统：写完代码点提交，它自动调用编译器编译，
再跑测试用例判分。判题用的编译参数和运行参数按省考场的口径配置，
解决的就是"在家能做、考场做不出"的问题。

开源地址：`github.com/yzh627/ExamDlgProj`（MIT 协议）

## 技术选型上，我为什么选了 Win32 + MFC

这个项目有个很硬的约束：**学生机的环境不能假设**。

机房电脑经常缺运行库、系统版本混杂、UAC 策略各异。所以我做了这些选择：

**1. 静态链接 CRT（`/MT`）**

主程序不依赖目标机装没装 VC++ 运行库，双击就能跑。
代价是包大了几 MB，但对"发到 U 盘让老师批量装机"这个场景来说，
少一个出问题的环节比省 3 MB 重要得多。

**2. 同时编译 x64 和 x86**

老机房的 32 位系统还在跑，所以两个架构都出，装的时候自动选。
代价是构建时间翻倍，但装机时不用问学生"你系统是几位的"。

**3. asInvoker 权限**

安装程序不提权。备考工具不需要管理员权限，
在域环境下也不会因为权限策略装不上。

**4. 加密题库内嵌**

题库不是明文 txt 打包进安装包，而是打包成加密的 `questions.dat`，
再内嵌到安装程序的资源段。理由很单纯：题库是这套工具的核心内容，
明文躺在安装包里很容易被单独抽出来传。

## 我自己写的安装器，没用 NSIS

这是整件事里我最花时间的部分。

**为什么不用现成的？** 我看了几个主流方案，装出来的东西有几个问题：
体积涨得厉害、卸载时容易留残留、没法自定义"非空目录先问一句"这种交互。

**payload 怎么塞进去的？** 全部塞在 PE 的 `.rsrc` 资源段：

```
安装程序（约 5.7 MB）
└── .rsrc
    ├── IDR_PAYLOAD_EXE        x64 主程序    2.8 MB
    ├── IDR_PAYLOAD_EXE32      x86 主程序    2.2 MB
    ├── IDR_PAYLOAD_BANK       加密题库      295 KB
    ├── IDR_PAYLOAD_UNINST     卸载程序      227 KB
    ├── IDR_PAYLOAD_MANIFEST   清单
    └── IDR_PAYLOAD_SUPPORT    界面图
```

安装时用 `FindResource` + `LoadResource` 逐个挖出来释放到磁盘。
**整个安装包只有一个 exe，双击即用，不需要解压中间层。**

**静默安装脚本的"验明正身"**

批量装机时会遇到这种情况：老师的 U 盘里可能有乱七八糟的 exe，
脚本不该随便挑一个就装。所以加了三重校验，宁缺毋滥：

```
粗筛：文件名含「对口/升学/练习/河北/中职/程序设计」之一
      体积在 1 MB ~ 40 MB 之间
      名字带「卸载」的直接排除
      ↓
细验（过其一即可）：
  A) certutil 算 SHA256，与内嵌校验值比对    → 同版本必然命中
  B) 读文件版本信息：ProductName 含「对口升学」
     且 CompanyName 含「一个中职生」
     且 FileDescription 含「安装程序」
      ↓
都不过：双击模式要求人工按 Y 确认；自动化模式直接拒绝（退出码 5）
```

有意思的是 B 这条。SHA256 会随版本变，但文件版本信息里的
ProductName / CompanyName 是稳定字段 —— 所以升级版本后，
即使哈希对不上，只要还是本产品，还是能认出来。

## 顺手补了四轮安全加固

发布前我做了一次完整的二进制安全检查，把结果直接读 PE 的
`DllCharacteristics` 字段看，发现自己的项目"该开的一个没开"。

| 项 | 检查前 | 现在的构建配置 |
|---|---|---|
| ASLR | 已开 | 显式写死（`/DYNAMICBASE`） |
| DEP/NX | 已开 | 显式写死（`/NXCOMPAT`） |
| **CFG 控制流保护** | **4 个 exe 全缺** | 已加 `/guard:cf` |
| **CET 影子栈**（x64） | **缺** | 已加 `/CETCOMPAT` |
| **`/GS` 栈保护** | 只靠默认值 | 显式写死 |
| **数字签名** | **无** | 见后文 |

CFG 那个尤其典型。我 grep 了一遍工程文件：

```
$ grep -c ControlFlowGuard ExamDlgProj.vcxproj
0
```

**整个项目在编译层面就没开过控制流保护。** 而 `vcxproj` 里
`SDLCheck`、`BufferSecurityCheck` 这些关键词的出现次数也全是 0 ——
不是关了，是从来没打开过。

顺便一个坑：`/CETCOMPAT` **x86 不支持**，脚本里得按架构分别处理，
不能一股脑往上加，否则 x86 那条构建会直接报错。

**为什么这么在意？** 因为这个软件要下发到几十台学生机上，
判题逻辑又涉及调用编译器执行代码，攻击面不算小。

## 数字签名这段，我卡了两次

Windows 11 从 22H2 起默认开着 Smart App Control，
它会检查**执行链上的每一个二进制** —— 主程序、安装器、卸载器、
安装时释放出来的临时文件，一个都不能是未签名的。

**所以 4 个 exe 我全签了**，不是签主程序就算完。

第二次卡在免费方案上。我找到 SignPath Foundation（给开源项目免费签名的公益组织），
申请了，被拒了。理由很直白：

> This isn't a judgment on the quality or potential of your work, it's purely
> about the level of **public visibility**.

GitHub stars、外部文章、机构背书 —— 仓库当时刚建，一天都没有。
这话说得其实没毛病，但我当时确实拿不出这些信号。

**顺带纠正一个我原先搞错了的事**：我之前以为买张 EV（增强验证）证书
就能让 SmartScreen 立刻放行。查了微软的文档才发现，
**2024 年 8 月微软更新 Trusted Root Program 时已经取消了这个豁免**，
现在 OV 和 EV 的信誉建立方式完全一样，都靠下载量积累。

微软文档里的原话是：

> 仅为了避免 SmartScreen 警示而支付 EV 溢价（每年 $400+）**已不再合理**

**所以如果你也在考虑买 EV 证书省 SmartScreen，别花这个钱。**

**"签名"真正的价值**是这三件事，不是消除蓝窗：
1. 消除"未知发布者"
2. 证明文件下载后未被篡改
3. 让排查"这文件是不是你说的那个"有据可查

蓝窗在初期一定会出现，这是 Windows 的机制在起作用，不是程序有问题。

## 构建从"本机跑"搬到 CI，炸出了四个雷

我把整个构建搬到了 GitHub Actions，因为代码签名要求构建过程可审查。
结果在干净环境里连续炸了四次，**每一个都是本机侥幸没暴露的问题**：

**① 版本探测被功能目录骗了**

```powershell
# 我原来的写法：挑"最新"的 SDK
Get-ChildItem $inc -Directory | Sort-Object Name -Descending | Select -First 1
```

`Windows Kits\10\Include\` 下不只有版本目录，还有 `wdf`（驱动开发包）这种功能目录。
**字符串倒序时 `'w'` 的 ASCII 值比数字大，所以 `wdf` 会被选中**，
拼出 `bin\wdf\x64\mt.exe` 这种不存在的路径。

报错说"没找到 mt.exe"，让我以为是 SDK 没装对 —— 真因却是版本探测写错了。

**② 临时目录指向不存在的路径**

```powershell
$env:TMP = Join-Path $proj 'x64\Debug'   # 这个目录只在我本机存在
```

链接器把 `.ilk` / `.pdb` 写到 TMP/TEMP。干净 checkout 上没这个目录，
链接就报 `LNK1104`。本机"能跑"纯粹是因为我以前编过 Debug 版。

**③ 工具链没装**

`microsoft/setup-msbuild` 只装 MSBuild 本体，**不含 C++ 编译器**。
而且只用 `--includeRecommended` 装出来的是 WDF SDK，`mt.exe` 在主 SDK 里。

**④ 辅助步骤掩盖真错误**

```yaml
- name: Upload artifacts
  if: always()      # ← 本意是"无论成败都上传"
```

构建失败时 `out\` 是空的，上传步骤照样跑，然后报
「未发现带有该路径的文件」，**把真正的 SDK 错误盖住了**。
诊断时要绕一圈才知道该看哪。

**这四个雷的共同点**：本机环境恰好提供了某些东西，脚本没检查。
CI 是个干净环境，专门用来炸出这类问题。

## 顺手加的自检脚本

现在发布前会跑一遍 `tools\check_release_signing.ps1`，四项：

1. **私钥泄露排查** —— 扫仓库里有没有 `.pfx`/`.pem`/`.p8`，
   扫脚本里有没有明文口令，断言签名用的是保管库引用而不是 `-f` 指定证书文件
2. **签名状态** —— 4 个文件是否都 `Valid`，是否都带 RFC3161 时间戳
3. **加固标志** —— 直接读 PE 的 `DllCharacteristics`，检查 ASLR/DEP/CFG
4. **产物一致性** —— bat 内嵌哈希、zip 成员、磁盘三处是否一致

这里有个设计上的取舍值得说：

**验签那步，对"未签名"只警告不失败。** 因为还没配签名时那是正常状态，
要是直接 fail 掉，没签名就永远发不出包了。

但真正的风险是**"以为签了其实没签"** —— SignPath 因为策略不匹配可能拒签，
CI 却显示绿灯。所以我的做法是：

- 单独检查 `signed\` 目录，只有"目录存在但一个都没签成功"才警告
- 日志里把每个文件的签名状态逐条列出来，不让它藏在汇总里

第 4 项能抓到一类隐蔽问题：装完程序忘了同步 bat 里的校验值。
这不会报错，只会让静默安装退到「文件版本信息」那条次优路径 ——
用户看到"版本与内嵌校验值不同"这句提示会一头雾水。

## 一点感想

这个项目从"一个想法"到"能发到几十台学生机上"，
最花时间的不是功能，是**边界情况**：

- 学生机的系统版本、权限、磁盘路径都是不可控的
- 一个.exe 要同时管安装、卸载、升级、目录冲突、非空目录确认
- 老师批量装机时，U 盘里可能有各种奇奇怪怪的文件

每一个"能跑通"背后，都有一个"不跑通就装不上"的对立面。

不过看到学生能用它练题，值了。
